## Introduction

Zarf is happy to announce `v1.0.0`. This milestone marks our commitment to stable releases, backward compatibility, and long-term support.

## v1beta1 Package Schema

A package schema defines the fields and structure of the `zarf.yaml` package definition. Zarf `v1.0.0` introduces a new version of that format, `v1beta1`, to make packages easier to author and maintain. It introduces reusable [published components](/commands/zarf_component_publish/) and a dedicated [templating workflow](/commands/zarf_dev_template/), while removing deprecated features and reorganizing keys from the previous format, `v1alpha1`.

### v1alpha1 Deprecation

The legacy package schema, `v1alpha1`, is deprecated in `v1.0.0`. However, we know there are countless existing `v1alpha1` packages supporting many critical systems across the world. To accommodate, we are giving an extended deprecation period for users to migrate. Zarf will support `v1alpha1` packages through August 2027, nine months after the `v1.0.0` release in November 2026.

On release of `v1.0.0`, Zarf will log a warning when `v1alpha1` packages are used. Starting in May 2027, create time operations such as `package create`, `publish`, and `sign` will require `--features=v1alpha1=true` for continued use. Deploy time operations will require the feature flag starting in June 2027.

Removing packages will operate without a feature flag until `v1alpha1` is fully unsupported. Follow the [`v1alpha1` to `v1beta1` migration guide](/best-practices/v1alpha1-to-v1beta1/) to update existing package definitions.

## Init Package

The default init package has migrated to v1beta1. Note that deployment must be configured through values instead of variables. The v1beta1 init package has a built-in migration guide through `zarf package inspect attachments --keys=migration` or find it at [MIGRATION.md](https://github.com/zarf-dev/zarf/blob/main/packages/init/v1beta1/MIGRATION.md).

The flag `--storage-class` has been removed from `zarf init`. Storage class can be configured through `registry.persistence.storageClass` and `gitServer.persistence.storageClass`. Additionally, the default storage class for the registry and Git server is the default storage class in the cluster. Previously, Zarf assigned a default storage class based on the distribution.

## Deployed Package State

Starting in v1.0, [deployed package secrets](/ref/packages/#deployed-packages) contain deploy configuration and increased deployment status fidelity. This information will enable additional features described in the [Enhanced State Management ZEP](https://github.com/zarf-dev/proposals/blob/main/0026-enhanced-state-management/README.md). Failure to write package state will now cause deploy to error. To prevent oversized secret write failures, secrets are now gzip-compressed.

Pre-v1.0 Zarf versions cannot read the gzipped secrets v1.0+ creates. Old CLIs may fail when accessing deployed packages created with v1.0+.

### Removed Features

Notable features removed in `v1.0.0`:

- The Zarf artifact server, which used Gitea to store artifacts such as npm packages, was removed due to limited adoption
- `zarf tools registry export`: Removed as registry commands focus on generic OCI operations, and container image exports were outside this scope.
- The SBOM viewer: Zarf no longer produces HTML files for human-friendly SBOM reading.
- Older Docker engine compatibility: Pulling images from a local Docker daemon now requires Docker Engine `25.0.0` or later
