The actual capabilities that Zarf Packages provide are defined within named components.

These components define what dependencies they have along with a declarative definition of how they should be deployed.

Each package can have as many components as the package creator wants but a package isn't anything without at least one component.

## What can be Packaged?

The following types of software can be rolled into a Zarf Package:

- Container images + artifacts: to serve images and OCI artifacts for clusters and other consumers to pull.

### Helm Charts

<Properties apiVersion="v1beta1" item="Component" include={["charts"]} />

Charts using the `local.path` key can be:

- Relative paths to either a file or directory (from the `zarf.yaml` file)

Remote charts can be:

- A Git repository using `git.url`, with `git.ref` selecting the revision and `git.path` selecting the chart directory
- An OCI registry using `oci.url` (oci://), with `oci.ref` selecting a tag or digest
- A Helm repository using `helmRepository.url` (http/https), with `helmRepository.name` and `helmRepository.version` selecting the chart

:::note

To use a private Helm repository the repo must be added to Helm. You can add a repo to Helm with the [`helm repo add`](https://helm.sh/docs/helm/helm_repo_add/) command or the equivalent internal `zarf tools helm repo add` command.

:::

#### Post-Renderers

Post-renderers patch a chart's rendered manifests before Zarf deploys them. Use them for changes that the chart's values do not expose, such as a `securityContext` on a hook Job, extra tolerations, or a different image. They follow the same model as Flux [`HelmRelease` post-renderers](https://fluxcd.io/flux/components/helm/helmreleases/#post-renderers). Each entry runs an inline Kustomize build over the chart's output, so you don't need to fork the chart.

:::note

Post-renderers are only available in `zarf.dev/v1beta1` packages. Packages that use them require Zarf `v1.1.0` or later to deploy. Zarf adds this requirement to the package automatically.

:::

Prefer chart values whenever the chart exposes a setting. Use post-renderers for the gaps. The [helm-post-renderers example](/ref/examples/helm-post-renderers/) hardens the Velero chart through values, then uses post-renderers for a hook Job that the values can't reach:

<ExampleYAML src={import("../../../../../examples/helm-post-renderers/zarf.yaml?raw")} component="velero" />

| Field | Description |
| --- | --- |
| `postRenderers` | Ordered list of post-renderers. Each entry receives the output of the previous entry. |
| `postRenderers[].kustomize.patches[].patch` | Required. An inline strategic merge patch (a YAML object) or JSON 6902 patch (a YAML list of operations). |
| `postRenderers[].kustomize.patches[].target` | Optional. Selects the resources to patch by `group`, `version`, `kind`, `name`, `namespace`, `labelSelector`, and `annotationSelector`. `name` and `namespace` accept regular expressions. JSON 6902 patches require a `target`. |
| `postRenderers[].kustomize.images[]` | Overrides container images by `name`, setting at least one of `newName`, `newTag`, or `digest`. |
| `postRenderers[].kustomize.enableTemplating` | Renders this entry's patches and image fields with [Zarf templating](/ref/package-values/#templating) when the chart is rendered. Defaults to `false`. |
| `postRenderStrategy` | Selects which documents post-renderers receive: `nohooks` (default), `combined`, or `separate`. |

A post-renderer entry must have at least one patch or image. Every strategic merge patch document must set `kind` and `metadata.name`, even when the patch has a `target`, and a patch with a `target` can contain only one document.

Always set a `target` when you can:

- A patch with a `target` is silently skipped when the target selects nothing, as in Kustomize and Flux. Double-check the kind, name, and namespace you select, and run [`zarf dev inspect manifests`](/commands/zarf_dev_inspect_manifests/) to confirm that the patch applied.
- A strategic merge patch without a `target` patches the resource that matches its `apiVersion`, `kind`, and `metadata.name`. It must match a resource in every pass it runs in, or rendering fails. With `separate`, that includes the hooks pass when the chart has hooks. With `nohooks`, it can't match a hook.

##### Helm Hooks

Charts often run [Helm hooks](https://helm.sh/docs/topics/charts_hooks/), such as migration or CRD upgrade Jobs. `postRenderStrategy` controls whether post-renderers see them:

- `nohooks` (default): post-renderers receive only the chart's regular resources. Hooks are deployed unchanged.
- `combined`: hooks and regular resources pass through each post-renderer together, in one Kustomize build. Kustomize requires unique resources, so this fails when a hook and a regular resource share the same kind, name, and namespace, such as a ServiceAccount declared both ways.
- `separate`: hooks and regular resources each pass through the full post-renderer chain on their own. Use this to patch hooks in charts that `combined` can't handle. Every post-renderer runs on both passes, so give hook patches a `target` to make them a no-op in the regular-resources pass.

Choose `nohooks` unless you need to patch a hook. Choose `combined` when a patch must see hooks and regular resources together. Otherwise, choose `separate`.

With `combined` and `separate`, Kustomize receives every hook in the chart, including `helm test` hooks. Kustomize can't process resources that set only `metadata.generateName`, so they can't be post-rendered. Charts with such hooks must use `nohooks`.

##### Order of Operations

Your post-renderers run before Zarf's own processing of the chart, so Zarf handles patched resources exactly like the rest of the chart. For example, a namespace or `zarf connect` Service label set by a patch gets Zarf's usual handling. In the cluster, the Zarf agent still rewrites patched image and Git references to the Zarf registry and Git server.

Zarf applies post-renderers everywhere it renders a chart: `zarf package deploy`, `zarf dev deploy`, `zarf package inspect manifests`, `zarf dev inspect manifests`, and `zarf dev find-images`.

##### Templating

When `enableTemplating: true` is set, Zarf renders that entry's `patch` strings and image `name`, `newName`, `newTag`, and `digest` strings whenever it renders the chart. Templates can use `.Values`, `.Pkg`, `.State`, and the [template functions](/ref/package-values/#templating) available to templated manifests. Sensitive `.State` fields require the component's `stateAccess`. With templating disabled (the default), Zarf uses the strings as written, so a literal `{{` passes through safely. When you create the package, Zarf checks that non-templated patches are valid YAML that Kustomize can load, and that JSON 6902 patches set a `target`. Templated patches are checked only after they are rendered.

Rendering values as JSON keeps them on one line, which avoids YAML indentation problems inside a patch:

```yaml
- kustomize:
    enableTemplating: true
    patches:
      - target:
          kind: Deployment
          name: my-app
        patch: |
          apiVersion: apps/v1
          kind: Deployment
          metadata:
            name: my-app
          spec:
            template:
              spec:
                tolerations: {{ .Values.tolerations | toJson }}
```

##### Caveats

- Helm usually renders resources without `metadata.namespace`. Kustomize treats a missing namespace as `default`, so `target.namespace` only matches resources whose manifests set a namespace explicitly. Select resources by kind, name, or labels instead.
- Helm installs CRDs from a chart's `crds/` directory directly, so post-renderers never see them. CRDs in `templates/` are post-rendered like any other resource.
- The component's `images` must list every image the post-rendered manifests use. That means the new references for any images that `images` overrides or patches replace. [`zarf dev find-images`](/commands/zarf_dev_find-images/) runs your post-renderers, so it reports the images the deployed chart will actually use.
- Post-renderers can't add new resources. To deploy extra resources next to a chart, use a [manifests](#kubernetes-manifests) entry.
- Kustomize drops resources annotated `config.kubernetes.io/local-config: "true"`, so post-rendered charts don't deploy them.
- When a component [imports](#merge-strategies) a chart and overrides it, the importing component's post-renderers run after the imported chart's, and its `postRenderStrategy`, if set, applies to all of them.
- Zarf CLIs older than `v1.1.0` refuse to deploy packages that use post-renderers. However, `zarf package inspect manifests` in an older CLI renders the charts without post-renderers.
- `zarf tools update-creds` re-applies the deployed post-renderers when it upgrades init package charts. Templated post-renderers only see the value overrides given at deploy time there, because Zarf doesn't record the package's default values. Templates that rely on package default values fail during `update-creds`.

Zarf dynamically generates a Helm Chart from the named manifest entries that you specify. This means that any given set of files under a manifest entry will be applied according to [Helm Chart template and manifest install ordering](https://github.com/helm/helm/blob/main/pkg/release/v1/util/manifest_sorter.go) and not necessarily in the order that files are declared. If ordering is important, consider moving each file into its own manifest entry in the `manifests` array.

### Container Images

<Properties apiVersion="v1beta1" item="Component" include={["images"]} />

Images can either be discovered manually, or automatically by using [`zarf dev find-images`](/commands/zarf_dev_find-images/). The image list is not limited to containers, any OCI image following the [Image Manifest specification](https://github.com/opencontainers/image-spec/blob/main/manifest.md) can be pulled

:::note

`zarf dev find-images` will find images for most standard manifests, kustomizations, and helm charts, however some images cannot be discovered this way as some upstream resources (like operators) may bury image definitions inside. For these images, `zarf dev find-images` also offers support for the draft [Helm Improvement Proposal 15](https://github.com/helm/community/blob/main/hips/hip-0015.md) which allows chart creators to annotate any hidden images in their charts along with the [values conditions](https://github.com/helm/community/issues/277) that will cause those images to be used.

:::

### Container Image Archives

<Properties apiVersion="v1beta1" item="Component" include={["imageArchives"]} />

Another way to bring OCI images into the package is via archives of [OCI layouts](https://specs.opencontainers.org/image-spec/image-layout/). Common ways to create OCI archives are through the [docker save](https://docs.docker.com/reference/cli/docker/image/save/) and [podman save --format=oci-archive](https://docs.podman.io/en/latest/markdown/podman-save.1.html) commands. The Docker engine version must be >= [25.0.0](https://docs.docker.com/engine/release-notes/25.0/#2500) as this was the release that the save command became compliant with the OCI layout specification.

An OCI layout can have any number of images, Zarf will pull all images that are listed in the sub-field `imageArchives.images`. If a listed image is not found in the archive then Zarf will error. In order for Zarf to find an image its [descriptor](https://specs.opencontainers.org/image-spec/descriptor/?v=v1.1.1) in the OCI-layout index.json must include the annotation "io.containerd.image.name" or "org.opencontainers.image.ref.name". `docker save` and `podman save` will automatically add at least one of these annotations.

Locally-built images that are not pulled from a public registry should be referenced under the reserved [`.internal`](https://www.icann.org/en/board-activities-and-meetings/materials/approved-resolutions-special-meeting-of-the-icann-board-29-07-2024-en#section2.a) top-level domain (for example `zarf.internal/my-app:1.0.0`). The `.internal` TLD will never resolve on the public internet, which avoids accidentally pulling an unexpected image if a registry reference is mistyped or rewriting fails. `zarf dev lint` emits a warning when an image archive image does not use a `.internal` domain.

```yaml
- name: image-archive
  description: "pull in an image from a tar archive"
  imageArchives:
  - path: image.tar
    images:
    - name: ghcr.io/fluxcd/helm-controller:v1.1.0
    - name: ghcr.io/fluxcd/image-automation-controller:v0.39.0
```

#### Tag-Based Git Repository Clone

Tag-based `git` repository cloning is the **recommended** way of cloning a `git` repository for air-gapped deployments because it wraps meaning around a specific point in git history that can easily be traced back to the online world. Tag-based clones are defined using `url` for the repository address and `ref.tag` for the tag, for example `url: https://github.com/zarf-dev/zarf.git` with `ref.tag: v0.15.0`.

A tag-based clone only mirrors the tag defined in the Zarf definition. The tag will be applied on the `git` mirror to a zarf-specific branch name based on the tag name (e.g. the tag `v0.1.0` will be pushed to the `zarf-ref-v0.1.0` branch).  This ensures that this tag will be pushed and received properly by the airgap `git` server.

:::note

If you would like to use a protocol scheme other than http/https, you can set `url` to something like the following: `ssh://git@github.com/zarf-dev/zarf.git`. Using this you can also clone from a local repo to help you manage larger git repositories: `file:///home/zarf/workspace/zarf`. Set `ref.tag` separately to select a tag such as `v0.15.0`.

:::

:::caution

Because Zarf creates long-lived mirrors of repositories in the airgap, it does not support shallow clones (i.e. `git clone --depth x`).  These may be present in build environments (i.e. [GitLab runners](https://github.com/zarf-dev/zarf/issues/1698)) and should be avoided.  To learn more about shallow and partial clones see the [GitHub blog on the topic](https://github.blog/2020-12-21-get-up-to-speed-with-partial-clone-and-shallow-clone).

:::

#### SHA-Based Git Repository Clone

In addition to tags, Zarf also supports cloning and pushing a specific SHA hash from a `git` repository, but this is **not recommended** as it is less readable/understandable than tag cloning. Commit SHAs are defined using `ref.commit`, for example `url: https://github.com/zarf-dev/zarf.git` with `ref.commit: c74e2e9626da0400e0a41e78319b3054c53a5d4e`.

A SHA-based clone only mirrors the SHA hash defined in the Zarf definition. The SHA will be applied on the `git` mirror to a zarf-specific branch name based on the SHA hash (e.g. the SHA `c74e2e9626da0400e0a41e78319b3054c53a5d4e` will be pushed to the `zarf-ref-c74e2e9626da0400e0a41e78319b3054c53a5d4e` branch). This ensures that this commit will be pushed and received properly by the airgap `git` server.

<ExampleYAML src={import("../../../../../examples/git-data/zarf.yaml?raw")} component="specific-hash" />

#### Branch-Based Git Repository Clone

If you need to clone a specific branch, Zarf also supports providing `ref.branch`, for example `url: https://repo1.dso.mil/big-bang/bigbang.git` with `ref.branch: release-1.54.x`. The branch name used by Zarf on deploy will be the upstream branch name, whereas tags and commits use the `zarf-ref-*` branch name.

#### Git Repository Full Clone

Full clones use a repository `url` without a `ref`, for example `url: https://github.com/stefanprodan/podinfo.git`. Full clones will contain **all** branches and tags in the mirrored repository rather than any one specific tag.

#### Merge Strategies

When merging components together Zarf will adopt the following strategies depending on the kind of primitive (`files`, `images`, `manifests`) that it is merging:

| Kind | Key(s) | Description |
| --- | --- | --- |
| Component Behavior | `name`, `description`, `optional`, `selector` | These keys control how Zarf interacts with a given component and will *always* take the value of the importing package component. They are not inherited from the imported component config's metadata or variant |
| Component Settings | `target.os`, `service` | These keys take the value of the importing component if it is not empty, otherwise they keep the imported value |
| Un'name'd Primitive Arrays | `files`, `imageArchives`, `repositories`, `stateAccess` | These keys will append the importing component's array to the end of the imported component's array |
| Actions | `actions` | Each lifecycle action list is appended to the imported list. Action defaults are replaced when provided by the importing component |
| Images | `images` | Images match by a nonempty `id` first, then by `name`. Matching images take nonempty fields from the importing component; unmatched images are appended |
| 'name'd Primitive Arrays | `charts`, `manifests` | Elements match by `name`. Matching elements merge their arrays and take nonempty settings from the importing component; unmatched elements are appended. Boolean options are enabled when either component sets them to `true` |

An importing component can override a chart source's version or reference, but cannot change its source type, URL, chart name, or path. When it overrides a chart, its [`postRenderers`](#post-renderers) are appended after the imported chart's, so they run last. Its `postRenderStrategy`, if set, replaces the imported one and applies to all of the chart's post-renderers.

Some package level fields from imported components will also be merged with the importing package.  These fields will be processed from the first component to the last component in a Zarf package definition.

| Kind | Field(s) | Description |
| --- | --- | --- |
| Un'name'd Primitive Arrays | `values.files` | The importing package definition's array will be appended to the end of the arrays from imported component configs. Duplicate paths are collapsed, with the first occurrence retained so the earliest position in the merge order is preserved. |
| Global Behavior | `values.schema` | Schemas are merged with the importing package's schema taking precedence, followed by earlier component imports. Nested imports have lower precedence than the component importing them |

## Deploying Components

When deploying a Zarf package, components are deployed in the order they are defined in the `zarf.yaml`.

The `zarf.yaml` configuration for each component also defines whether the component is optional using `optional: true`. Components are required by default and are always deployed without any additional user interaction, while optional components are printed out in an interactive prompt asking the user if they wish to deploy the component.

If you already know which components you want to deploy, you can do so without getting prompted by passing the components as a comma-separated list to the `--components` flag during the deploy command.

```bash
# deploy all required components, prompting for optional components
$ zarf package deploy ./path/to/package.tar.zst

# deploy all required components, ignoring optional component prompts
$ zarf package deploy ./path/to/package.tar.zst --confirm

# deploy all required components plus optional-component-1 and optional-component-2
$ zarf package deploy ./path/to/package.tar.zst --components=optional-component-1,optional-component-2
```

:::tip

You can deploy components in a package using globbing as well. The following would deploy all components regardless of optional status:

```bash
# deploy all required and optional components
$ zarf package deploy ./path/to/package.tar.zst --components='*'
```

You can also exclude optional components from the CLI with a leading dash (`-`) (similar to how you can exclude search terms in a search engine).

```bash
# deploy all required components and optional components except optional-component-2
$ zarf package deploy ./path/to/package.tar.zst --components='*,-optional-component-2'
```

When a component matches multiple selectors, the last matching selector takes precedence. For example, `--components='-*,optional-component-1'` excludes optional components except `optional-component-1`. Reversing the selectors excludes it too. Required components remain selected. Previously exclusions always took precedence; place exclusions last to retain that behavior.

:::
